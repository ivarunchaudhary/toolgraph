This is a research benchmark on a demo catalog

It runs on a built-in demo set of tools modelled on well-known services, not on your workspace. Retrieval runs real HydraDB queries, the planner is a real model, and what it learns is written to HydraDB. Execution is simulated: no tool actually runs. A checker marks a task solved when every tool in the plan was handed to the agent, each tool's required inputs (an ID, a channel) were already available, and the task's goal was produced.

    Architecture

    The agent asks for tools per task instead of loading the whole catalog.

    Graph schema

    • (Tool)-[:PROVIDES {weight}]->(Capability) what a tool is for
    • (Tool)-[:CONSUMES]->(DataType) required inputs (typed: a Slack channel id is not a Discord one)
    • (DataType)-[:PRODUCED_BY]->(Tool) who can produce an input: the prerequisite edge vector search cannot see
    • (Tool)-[:PART_OF]->(Server) MCP server membership
    • (Intent)-[:SOLVED_WITH {weight}]->(Tool) learned: task cluster → tools that worked
    • (Tool)-[:NEXT {weight}]->(Tool) learned: "often called after"

    Learning rules

      Why frontier traversal

      The first version sent one deep UNION ALL query (one round trip). It was fine at 134 tools, but at 1,000 tools its p50 was ~1.5 s, because 4-level chain patterns expand before filtering. Now ToolGraph sends 1 seed query plus 1 id-anchored hop query per prerequisite level, keeping only producers near the task (named servers + servers of the most similar tools). Results are identical at 134 tools, and at 10,000 tools the p50 is ~200 ms. Both variants are measured in results/scale.json.
